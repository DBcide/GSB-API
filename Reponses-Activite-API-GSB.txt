1.1 - Schema du parcours d'une requete POST /api/visiteurs

Lorsqu'un client effectue une requete POST vers /api/visiteurs, la requete
traverse plusieurs couches de l'application selon une architecture en trois
tiers (three-tier architecture).

CONSIGNE POUR LE GRAPHIQUE :
Creer un diagramme de flux vertical avec les etapes suivantes :

[CLIENT]
   |
   | POST /api/visiteurs
   | Header: Authorization: Bearer <token>
   | Body: {nom, prenom, email, ...}
   v
[MIDDLEWARE RATE LIMITER] (src/middlewares/Ratelimiter.ts)
   |
   | Verification : < 10 requetes/minute ?
   |--- NON --> [ERREUR 429] "Trop de requetes"
   |
   |--- OUI
   v
[MIDDLEWARE AUTH] (src/middlewares/auth.ts)
   |
   | 1. Extraction du token depuis le header Authorization
   | 2. Verification du token avec JWT_SECRET
   | 3. Decodage du payload (visiteurId, role)
   |--- INVALIDE --> [ERREUR 401] "Unauthorized request"
   |
   |--- VALIDE
   v
[ROUTER] (src/routes/Visiteur.ts)
   |
   | Mapping de la route vers le controleur
   | router.post('/', authMiddleware, controller.create)
   v
[CONTROLLER] (src/controllers/Visiteur.ts)
   |
   | Methode : create(req, res)
   | 1. Extraction des donnees depuis req.body
   | 2. Appel du service : service.createVisiteur(req.body)
   | 3. Gestion de la reponse HTTP
   v
[SERVICE] (src/services/Visiteur.ts)
   |
   | Methode : createVisiteur(data)
   | 1. Verification si l'email existe deja
   | 2. Creation d'une instance du modele Mongoose
   | 3. Validation des donnees selon le schema
   | 4. Sauvegarde en base de donnees
   v
[MODEL] (src/models/Visiteur.ts)
   |
   | Schema Mongoose avec validations :
   | - nom : requis, type String
   | - prenom : requis, type String
   | - email : requis, unique, lowercase
   | - password : requis, type String
   | - tel : requis, type String
   | - dateEmbauche : requis, type Date
   v
[BASE DE DONNEES MongoDB Atlas]
   |
   | Insertion du document dans la collection "visiteurs"
   |
   v
[REPONSE]
   |
   | Retour vers le client :
   | - Code 201 (Created) si succes
   | - Code 400 (Bad Request) si erreur de validation
   | - Code 500 (Internal Server Error) si erreur serveur

EXPLICATION :

Cette architecture en couches permet une separation claire des responsabilites.
Chaque couche a un role specifique :

- Les MIDDLEWARES (rate limiter, auth) filtrent et securisent les requetes
  avant qu'elles n'atteignent la logique metier.

- Le ROUTER definit les points d'entree de l'API et associe chaque route a
  une methode du controleur.

- Le CONTROLLER gere les aspects HTTP (req/res), extrait les donnees de la
  requete et delegue le traitement au service.

- Le SERVICE contient la logique metier (verification de l'existence de
  l'email, gestion des erreurs de validation). C'est ici que se trouvent
  les regles metier de l'application.

- Le MODEL definit la structure des donnees et les regles de validation au
  niveau de la base de donnees avec Mongoose.

Cette separation facilite la maintenance, les tests unitaires et l'evolution
du code.

1.2 - Role du pattern Singleton dans Database.ts

Le pattern Singleton est un patron de conception (design pattern) qui garantit
qu'une classe ne possede qu'une seule instance dans toute l'application, et
fournit un point d'acces global a cette instance.

FICHIER CONCERNE : src/config/database.ts

Dans notre projet GSB, la classe Database utilise le pattern Singleton pour
gerer la connexion a MongoDB. Voici comment cela fonctionne :

1. CONSTRUCTEUR PRIVE (ligne 17) :

   private constructor() {}

   Le constructeur est declare "private", ce qui empeche de creer des
   instances de la classe depuis l'exterieur avec "new Database()".

2. INSTANCE STATIQUE (ligne 13) :

   private static instance: Database;

   La classe stocke une reference statique vers sa propre instance unique.

3. METHODE getInstance() (lignes 23-28) :

   public static getInstance(): Database {
     if (!Database.instance) {
       Database.instance = new Database();
     }
     return Database.instance;
   }

   Cette methode verifie si une instance existe deja. Si non, elle en cree
   une. Si oui, elle retourne l'instance existante.

AVANTAGES DU SINGLETON DANS CE CONTEXTE :

A. Connexion unique a MongoDB :
   MongoDB ne necessite qu'une seule connexion partagee entre toutes les
   parties de l'application. Creer plusieurs connexions serait inefficace
   et pourrait causer des problemes de performances.

B. Economie de ressources :
   Une seule connexion TCP vers MongoDB au lieu de plusieurs connexions
   paralleles qui consommeraient inutilement des ressources serveur.

C. Etat partage :
   La variable "isConnected" (ligne 14) permet de savoir si la connexion
   est active sans tenter de se reconnecter a chaque fois.

D. Point d'acces global :
   N'importe quelle partie de l'application peut acceder a la connexion
   via Database.getInstance().connect() sans avoir a passer la reference
   de connexion comme parametre.

EXEMPLE D'UTILISATION :

Dans server.ts (ligne 36) :
   this.database = Database.getInstance();

Puis dans la methode initializeDatabase (ligne 108) :
   await this.database.connect();

Meme si on appelle getInstance() plusieurs fois dans differents fichiers,
c'est toujours la meme instance qui est retournee.

1.3 - Pourquoi separer les routes, les controleurs et les services ?

La separation des routes, controleurs et services suit le principe de
separation des responsabilites (Separation of Concerns). Chaque couche a
un role bien defini et ne devrait pas s'occuper des preoccupations des
autres couches.

COMPARAISON AVEC UNE ARCHITECTURE MONOLITHIQUE :

Sans separation, tout le code pourrait etre dans le fichier de routes :

   // MAUVAISE PRATIQUE - Tout dans les routes
   router.post('/visiteurs', async (req, res) => {
     const token = req.headers.authorization?.split(' ')[1];
     const decoded = jwt.verify(token, process.env.JWT_SECRET);
     const existingVisiteur = await VisiteurModel.findOne({email: req.body.email});
     if (existingVisiteur) {
       return res.status(400).json({error: 'Email existe deja'});
     }
     const visiteur = new VisiteurModel(req.body);
     await visiteur.save();
     res.status(201).json(visiteur);
   });

Cette approche pose plusieurs problemes :
- Code difficile a lire et a maintenir
- Impossible de reutiliser la logique ailleurs
- Tests unitaires complexes (il faut mocker Express, MongoDB, JWT...)
- Violation du principe de responsabilite unique

AVEC SEPARATION EN 3 COUCHES :

1. ROUTES (src/routes/Visiteur.ts) :
   Role : Definir les points d'entree de l'API (endpoints)

   Responsabilites :
   - Declarer les chemins (paths) : /visiteurs, /visiteurs/:id
   - Specifier les methodes HTTP : GET, POST, PUT, DELETE
   - Appliquer les middlewares specifiques : authMiddleware, validation
   - Router vers le bon controleur

   Exemple (lignes 13-14) :
   router.post('/', authMiddleware, controller.create);

   La route ne contient AUCUNE logique metier, juste du routage.

2. CONTROLEURS (src/controllers/Visiteur.ts) :
   Role : Gerer les aspects HTTP (requete/reponse)

   Responsabilites :
   - Extraire les donnees de req.body, req.params, req.query
   - Appeler les methodes du service avec les bonnes donnees
   - Transformer les resultats en reponses HTTP
   - Gerer les codes de statut (200, 201, 400, 404, 500)
   - Formater les erreurs pour le client

   Exemple (lignes 6-13) :
   create = async (req: Request, res: Response) => {
     try {
       const visiteur = await service.createVisiteur(req.body);
       res.status(201).json(visiteur);
     } catch (error: any) {
       res.status(400).json({ error: error.message });
     }
   }

   Le controleur ne contient AUCUNE logique metier, il delegue au service.

3. SERVICES (src/services/Visiteur.ts) :
   Role : Contenir la logique metier et interagir avec les modeles

   Responsabilites :
   - Valider les regles metier (ex: email unique)
   - Effectuer les transformations de donnees (ex: hash du password)
   - Interagir avec la base de donnees via les modeles
   - Gerer les transactions complexes
   - Transformer les erreurs Mongoose en erreurs metier comprehensibles

   Exemple (lignes 15-34) :
   public async createVisiteur(data: ICreateVisiteur): Promise<IVisiteurDocument> {
     try {
       const existingVisiteur = await VisiteurModel.findOne({ email: data.email });
       if (existingVisiteur) {
         throw new Error(`Un visiteur avec l'email ${data.email} existe deja`);
       }
       const visiteur = new VisiteurModel(data);
       await visiteur.save();
       return visiteur;
     } catch (error: any) {
       if (error.name === 'ValidationError') {
         const messages = Object.values(error.errors).map((err: any) => err.message);
         throw new Error(`Validation echouee: ${messages.join(', ')}`);
       }
       throw error;
     }
   }

AVANTAGES DE CETTE SEPARATION :

A. MAINTENABILITE :
   Si je dois modifier la logique de verification d'email, je sais exactement
   ou aller : dans le service. Je n'ai pas a chercher dans des fichiers de
   routes ou de controleurs.

B. REUTILISABILITE :
   La methode createVisiteur() du service peut etre appelee depuis plusieurs
   controleurs differents (ex: une route admin, une route publique, un script
   CLI). La logique n'est ecrite qu'une seule fois.

C. TESTABILITE :
   Je peux tester le service independamment avec des tests unitaires en
   mockant uniquement le modele Mongoose. Je n'ai pas besoin de mocker
   Express ou HTTP.

D. EVOLUTION :
   Si demain on doit ajouter une API GraphQL en plus de REST, on peut
   reutiliser les services existants sans dupliquer la logique metier.

E. TRAVAIL EN EQUIPE :
   Plusieurs developpeurs peuvent travailler simultanement : un sur les
   routes, un autre sur les services, sans conflit de merge git.

F. PRINCIPE SOLID :
   Cette architecture respecte le principe de responsabilite unique (S dans
   SOLID) : chaque classe a une seule raison de changer.

2.1 - Mecanisme de verification mis en place

Pour verifier les donnees envoyees au niveau de la requete HTTP, j'ai mis en
place un middleware de validation base sur la bibliotheque "express-validator".

FICHIER CONCERNE : src/middlewares/validation.ts

Ce middleware intercepte les requetes AVANT qu'elles n'atteignent le controleur
et verifie que les donnees respectent des regles predefinies.

IMPLEMENTATION :

1. MIDDLEWARE DE GESTION DES ERREURS (lignes 8-18) :

   export const handleValidationErrors = (req: Request, res: Response, next: NextFunction) => {
     const errors = validationResult(req);
     if (!errors.isEmpty()) {
       res.status(400).json({
         success: false,
         errors: errors.array()
       });
       return;
     }
     next();
   };

   Ce middleware verifie si des erreurs de validation ont ete detectees.
   Si oui, il renvoie une reponse 400 avec la liste des erreurs.
   Si non, il appelle next() pour passer au controleur.

2. VALIDATION POUR LA CREATION DE COMPTE (lignes 23-51) :

   export const validateCreerCompte = [
     body('email')
       .isEmail()
       .withMessage('Email invalide')
       .normalizeEmail(),

     body('password')
       .isLength({ min: 8 })
       .withMessage('Le mot de passe doit contenir au moins 8 caracteres')
       .matches(/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)/)
       .withMessage('Le mot de passe doit contenir au moins une majuscule, une minuscule et un chiffre'),

     body('nom')
       .trim()
       .isLength({ min: 2, max: 50 })
       .withMessage('Le nom doit contenir entre 2 et 50 caracteres')
       .customSanitizer(value => xss(value)),

     body('prenom')
       .trim()
       .isLength({ min: 2, max: 50 })
       .withMessage('Le prenom doit contenir entre 2 et 50 caracteres')
       .customSanitizer(value => xss(value)),

     body('tel')
       .trim()
       .matches(/^[0-9]{10}$/)
       .withMessage('Le numero de telephone doit contenir 10 chiffres'),

     body('dateEmbauche')
       .isISO8601()
       .withMessage('Date d\'embauche invalide'),

     handleValidationErrors
   ];

REGLES DE VALIDATION IMPLEMENTEES :

- EMAIL : Doit etre au format email valide. Normalise (lowercase, trim).
- PASSWORD : Minimum 8 caracteres, doit contenir au moins une majuscule,
  une minuscule et un chiffre.
- NOM/PRENOM : Entre 2 et 50 caracteres. Protection XSS avec sanitization.
- TEL : Exactement 10 chiffres.
- DATE EMBAUCHE : Format ISO8601 (YYYY-MM-DD).

3. APPLICATION DU MIDDLEWARE DANS LES ROUTES (lignes 9-10 de Visiteur.ts) :

   router.post('/creeruncompte', validateCreerCompte, controller.creerUnCompte);

   Le middleware validateCreerCompte est applique AVANT le controleur.

2.3 - A quel moment la verification se fait

La verification se fait en AMONT du controleur, au niveau du middleware de
validation.

ORDRE D'EXECUTION :

1. La requete arrive sur le serveur Express
2. Elle passe par le middleware de rate limiting (verification du nombre de requetes)
3. Elle arrive sur la route /api/visiteurs/creeruncompte
4. Express execute les middlewares dans l'ordre de declaration :
   a. validateCreerCompte (VERIFICATION ICI - ligne 23-51 de validation.ts)
   b. controller.creerUnCompte (ligne 15-44 de Visiteur.ts)

Si la validation echoue, le middleware handleValidationErrors (ligne 8-18 de
validation.ts) renvoie immediatement une erreur 400 et n'appelle PAS next().
Le controleur n'est donc JAMAIS execute.

Si la validation reussit, le middleware appelle next() et la requete continue
vers le controleur.

FICHIER CONCERNE : src/routes/Visiteur.ts (ligne 9)

   router.post('/creeruncompte', validateCreerCompte, controller.creerUnCompte);
                                 ^^^^^^^^^^^^^^^^^
                                 VALIDATION ICI AVANT LE CONTROLEUR

Les messages d'erreur proviennent de deux endroits selon la nature de l'erreur.

CAS 1 : ERREURS DE VALIDATION EXPRESS-VALIDATOR

Provenance : src/middlewares/validation.ts

.withMessage().

Exemple (lignes 29-32) :

   body('password')
     .isLength({ min: 8 })
     .withMessage('Le mot de passe doit contenir au moins 8 caracteres')
                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                  MESSAGE PERSONNALISE DEFINI ICI

Quand la validation echoue, express-validator collecte tous les messages
d'erreur et les stocke dans un tableau. Le middleware handleValidationErrors
(ligne 8-18) recupere ces messages avec validationResult(req) et les envoie

3.3 - A quel moment la verification Mongoose se fait

La verification Mongoose se fait au moment de la sauvegarde en base de donnees,
dans la couche SERVICE.

ORDRE D'EXECUTION :

1. La requete arrive et passe les middlewares (si validation HTTP commentee)
2. Le controleur appelle le service (ligne 31 de Visiteur.ts controller) :
   const visiteur = await service.creerUnCompte(visiteurData);

3. Le service cree une instance du modele (ligne 49-56 de Visiteur.ts service) :
   const visiteur = new VisiteurModel({
     email: visiteurData.email,
     password: hashedPassword,
     nom: visiteurData.nom,
     prenom: visiteurData.prenom,
     tel: visiteurData.tel,
     dateEmbauche: visiteurData.dateEmbauche
   });

4. Le service tente de sauvegarder (ligne 57 de Visiteur.ts service) :
   await visiteur.save();
         ^^^^^^^^^^^^^^ VALIDATION MONGOOSE SE FAIT ICI

5. Mongoose execute les validations definies dans le schema AVANT d'inserer
   dans MongoDB. Si une validation echoue, Mongoose lance une ValidationError.

6. Le service catch l'erreur (lignes 63-69) et la transforme en message :
   catch (error: any) {
     if (error.name === 'ValidationError') {
       const messages = Object.values(error.errors).map((err: any) => err.message);

       throw new Error(errorMessage);
     }
     throw error;
   }

7. Le controleur catch l'erreur du service et renvoie un 400 (lignes 38-43) :
   catch (error: any) {
     res.status(400).json({
       success: false,
       message: error.message || 'Erreur lors de la creation'
     });
   }

3.4 - Provenance du message d'erreur Mongoose

Les messages d'erreur Mongoose proviennent de deux sources :

SOURCE 1 : MESSAGES PAR DEFAUT DE MONGOOSE

Quand une contrainte du schema n'est pas respectee, Mongoose genere
automatiquement un message d'erreur generique.

Exemples :
- Champ required manquant : "Path `nom` is required."
- Type incorrect : "Cast to Date failed for value \"invalid\" at path \"dateEmbauche\""
- Valeur unique violee : "E11000 duplicate key error"

Ces messages sont en anglais et assez techniques.

SOURCE 2 : TRANSFORMATION DANS LE SERVICE

Dans le service VisiteurService, le bloc catch intercepte les ValidationError
de Mongoose et les transforme en messages plus conviviaux.

FICHIER : src/services/Visiteur.ts (lignes 63-69)

   catch (error: any) {
     if (error.name === 'ValidationError') {
       const messages = Object.values(error.errors).map((err: any) => err.message);
       const errorMessage = `Validation echouee: ${messages.join(', ')}`;
       console.error('[ValidationError]', errorMessage);
       throw new Error(errorMessage);
     }
     console.error('[Error]', error);
     throw error;
   }

EXPLICATION :

1. Mongoose lance une ValidationError qui contient un objet "errors"
2. Chaque propriete de cet objet correspond a un champ invalide
3. On extrait tous les messages d'erreur avec .map((err: any) => err.message)
4. On les concatene avec .join(', ')
5. On ajoute un prefixe "Validation echouee: " pour plus de clarte
6. On lance une nouvelle Error avec ce message formate

Le controleur recupere ensuite ce message et le renvoie au client :

FICHIER : src/controllers/Visiteur.ts (lignes 38-43)

   catch (error: any) {
     res.status(400).json({
       success: false,
       message: error.message || 'Erreur lors de la creation'
     });
   }

AMELIORATION POSSIBLE :

On pourrait personnaliser les messages directement dans le schema avec
des validateurs personnalises :

   nom: {
     type: String,
     required: [true, 'Le nom est obligatoire'],
     minlength: [2, 'Le nom doit contenir au moins 2 caracteres']
   }

3.5 - Validations effectuees dans le contexte normal d'utilisation

Dans le contexte normal d'utilisation de l'API (avec tous les middlewares
actifs), DEUX NIVEAUX DE VALIDATION sont effectues successivement :

NIVEAU 1 : VALIDATION HTTP (Express-validator)
Fichier : src/middlewares/validation.ts
Moment : AVANT le controleur
Verifie :
- Format de l'email
- Complexite du mot de passe (min 8 caracteres, majuscule, minuscule, chiffre)
- Longueur du nom/prenom (2-50 caracteres)
- Format du telephone (10 chiffres)
- Format de la date (ISO8601)
- Sanitization XSS des champs texte

Si ce niveau echoue : Erreur 400 immediate, le controleur n'est pas execute.

NIVEAU 2 : VALIDATION MONGOOSE (Schema)
Fichier : src/models/Visiteur.ts
Moment : Lors de la sauvegarde en base (visiteur.save())
Verifie :
- Presence de tous les champs required
- Types de donnees corrects
- Unicite de l'email dans la base
- Validite des references (ObjectId pour portefeuille)

Si ce niveau echoue : Exception ValidationError catchee par le service,
transformee en message et renvoyee au client avec un code 400.

STRATEGIE DE DEFENSE EN PROFONDEUR (Defense in Depth) :

Cette double validation est une bonne pratique de securite appelee "defense
en profondeur". On ne fait pas confiance a un seul niveau de validation :

1. PREMIER NIVEAU (HTTP) :
   - Valide les donnees au plus tot dans le cycle de vie de la requete
   - Evite d'executer du code inutile si les donnees sont invalides
   - Fournit des messages d'erreur detailles et user-friendly
   - Protege contre les attaques XSS
   - Performance : Moins couteux que d'aller jusqu'a la base de donnees

2. DEUXIEME NIVEAU (Mongoose) :
   - Protection de dernier recours (last line of defense)
   - Protege meme si un developpeur oublie d'appliquer le middleware
   - Garantit l'integrite des donnees au niveau de la base
   - Protege contre les modifications directes du modele (scripts, tests)
   - Validation des contraintes de la base (unique, references)

EXEMPLE DE FLUX NORMAL :

Requete POST /api/visiteurs/creeruncompte avec body :
{
  "nom": "Dupont",
  "prenom": "Jean",
  "email": "jean.dupont@gsb.fr",
  "password": "SecurePass123",
  "tel": "0612345678",
  "dateEmbauche": "2024-01-15"
}

Etape 1 : Middleware validateCreerCompte
   -> Toutes les validations passent
   -> Appel de next()

Etape 2 : Controleur creerUnCompte
   -> Extraction des donnees
   -> Appel du service

Etape 3 : Service creerUnCompte
   -> Hash du password
   -> Creation de l'instance VisiteurModel
   -> Appel de visiteur.save()

Etape 4 : Validation Mongoose
   -> Verification des champs required : OK
   -> Verification des types : OK
   -> Verification unique email : OK
   -> Insertion dans MongoDB

Etape 5 : Reponse au client
   -> Status 201 Created
   -> Donnees du visiteur (sans le password)

CONCLUSION :

Dans le contexte normal, les validations HTTP attrapent 90% des erreurs de
saisie utilisateur, tandis que les validations Mongoose servent de filet de
securite pour les 10% restants et garantissent l'integrite des donnees a
long terme.

4.3 - A quoi sert le Mock dans le test

Le Mock (simulacre en francais) est une technique fondamentale des tests
unitaires. Un mock remplace un composant reel par une version controlee qui
simule son comportement.

DANS NOTRE CONTEXTE :

Nous testons la methode getVisiteurById() du SERVICE, mais cette methode
depend du MODELE Mongoose (VisiteurModel.findById).

Le probleme : Si on utilise le vrai modele Mongoose dans les tests :
- Il faudrait une connexion a MongoDB (lente, complexe)
- Les tests dependraient de l'etat de la base (donnees existantes)
- Les tests ne seraient plus unitaires mais d'integration
- Un probleme reseau ou base de donnees ferait echouer les tests

La solution : MOCKER le modele Mongoose

COMMENT CA MARCHE :

1. DECLARATION DU MOCK (ligne 5) :

   jest.mock('../../models/Visiteur');

   Cette ligne indique a Jest de remplacer le vrai VisiteurModel par une
   version mockee. Toutes les methodes du modele deviennent des fonctions
   vides que nous pouvons controler.

2. CONFIGURATION DES MOCKS CHAINABLES (lignes 18-25) :

   mockPopulate = jest.fn();
   mockSelect = jest.fn().mockReturnValue({ populate: mockPopulate });
   mockFindById = jest.fn().mockReturnValue({ select: mockSelect });

   (VisiteurModel.findById as jest.Mock) = mockFindById;

   Mongoose utilise une API chainable :
   VisiteurModel.findById(id).select('...').populate('...')

   Nous devons donc creer une chaine de mocks qui se retournent mutuellement.

3. CONTROLE DU COMPORTEMENT (exemple dans le test 1, ligne 41) :

   mockPopulate.mockResolvedValue(visiteurMock);

   Nous disons au mock : "Quand tu seras appele, retourne visiteurMock".
   C'est nous qui decidons ce que retourne la "fausse" base de donnees.

4. VERIFICATION DES APPELS (lignes 51-54) :

   expect(mockFindById).toHaveBeenCalledWith(visiteurId);
   expect(mockSelect).toHaveBeenCalledWith('nom prenom email portefeuille');
   expect(mockPopulate).toHaveBeenCalledWith('portefeuille', 'nom prenom specialite');

   Nous verifions que notre service appelle bien les bonnes methodes avec
   les bons parametres.

AVANTAGES DU MOCK :

A. ISOLATION COMPLETE :
   Le test ne depend que du code du service, pas de MongoDB, du reseau, ou
   de donnees existantes. C'est un veritable test UNITAIRE.

B. VITESSE :
   Pas de connexion reseau, pas d'I/O disque. Les tests s'executent en
   quelques millisecondes au lieu de plusieurs secondes.

C. PREDICTIBILITE :
   Nous controlons exactement ce que retourne la "fausse" base. Les tests
   donnent toujours le meme resultat (deterministes).

D. TESTS DE CAS LIMITES :
   Facile de tester des situations rares ou difficiles a reproduire :
   - Visiteur inexistant (test 2)
   - Erreurs de base de donnees
   - Timeouts
   - Donnees corrompues

E. VERIFICATION DU COMPORTEMENT :
   On peut verifier que le service utilise bien les bonnes methodes Mongoose
   (select, populate) avec les bons parametres.

ANALOGIE :

Imaginez que vous testez une voiture. Vous voulez verifier que l'ordinateur
de bord calcule correctement la consommation d'essence.

SANS MOCK :
Vous devez construire un vrai moteur, mettre de l'essence, rouler sur route...
Lent, couteux, plein de variables incontrolables (trafic, meteo).

AVEC MOCK :
Vous simulez le moteur : "Je te donne 10 litres d'essence et 100 km parcourus,
dis-moi la consommation". Rapide, isole, reproductible.

C'est exactement ce que nous faisons : nous simulons MongoDB pour tester
uniquement la logique du service.

A. Methode creerUnCompte (lignes 39-73) :

ETAPE 7 : CREATION DU MIDDLEWARE D'AUTHENTIFICATION

Fichier : src/middlewares/auth.ts

Contenu (lignes 10-29) :
   export const authMiddleware = (
     req: AuthenticatedRequest,
     res: Response,
     next: NextFunction
   ): void => {
     try {
       const authHeader = req.headers.authorization;
       if (!authHeader) {
         throw new Error('Authorization header is missing.');
       }

       const token = authHeader.split(' ')[1];
       const decodedToken = jwt.verify(
         token,
         process.env.JWT_SECRET as string,
         { algorithms: ['HS256'] }
       ) as DecodedToken;

       req.auth = {
         visiteurId: decodedToken.visiteurId,
         role: decodedToken.role
       };
       next();
     } catch (error) {
       res.status(401).json({ error: 'Unauthorized request' });
     }
   };

Fonctionnement :
1. Extrait le header Authorization
2. Recupere le token (partie apres "Bearer ")
3. Verifie la signature avec jwt.verify()
4. Si valide, decode le payload et l'ajoute a req.auth
5. Appelle next() pour continuer vers le controleur
6. Si invalide, renvoie 401 Unauthorized

ETAPE 8 : CREATION DU MIDDLEWARE DE VALIDATION

   Valide : email, password (8+ caracteres, majuscule, minuscule, chiffre),
   nom, prenom, tel (10 chiffres), dateEmbauche

B. validateConnexion (lignes 56-65) :
   Valide : email, password (non vide)

ETAPE 9 : CONFIGURATION DES ROUTES

6.1 - Bonnes pratiques de securite deja mises en oeuvre

A partir du document officiel ExpressJS sur les bonnes pratiques de securite
(https://expressjs.com/en/advanced/best-practice-security.html), voici les
mesures deja implementees dans notre projet GSB.

PRATIQUE 1 : UTILISER HELMET POUR SECURISER LES HEADERS HTTP

Implementation : src/server.ts (ligne 48)
   this.app.use(helmet());

Helmet est un middleware qui configure automatiquement plusieurs headers HTTP
de securite pour proteger l'application contre des attaques courantes :

- X-Content-Type-Options: nosniff
  Empeche les navigateurs de deviner le type MIME des fichiers

- X-Frame-Options: DENY
  Protege contre le clickjacking en empechant l'iframe de la page

- X-XSS-Protection: 1; mode=block
  Active le filtre XSS du navigateur

- Strict-Transport-Security
  Force l'utilisation de HTTPS (important en production)

- Content-Security-Policy
  Limite les sources de contenu autorisees

PRATIQUE 2 : VALIDER ET SANITISER LES ENTREES UTILISATEUR

Implementation : src/middlewares/validation.ts

Nous utilisons express-validator pour :

A. Validation des formats (lignes 24-27) :
   body('email')
     .isEmail()
     .withMessage('Email invalide')
     .normalizeEmail()

B. Validation de la complexite des mots de passe (lignes 28-32) :
   body('password')
     .isLength({ min: 8 })
     .matches(/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)/)

C. Limitation de la longueur des champs (lignes 34-36) :
   body('nom')
     .trim()
     .isLength({ min: 2, max: 50 })

D. Sanitization XSS (ligne 37) :
   .customSanitizer(value => xss(value))

E. Validation des numeros de telephone (lignes 43-46) :
   body('tel')
     .matches(/^[0-9]{10}$/)

Ces validations empechent l'injection de donnees malveillantes.

PRATIQUE 3 : UTILISER BCRYPT POUR HASHER LES MOTS DE PASSE

Implementation : src/services/Visiteur.ts (ligne 48)
   const hashedPassword = await bcrypt.hash(visiteurData.password, 10);

Bcrypt est un algorithme de hachage securise concu specifiquement pour les
mots de passe. Avantages :

- Hachage irreversible (one-way function)
- Salt automatique et unique pour chaque mot de passe
- Cout de calcul ajustable (10 rounds = 2^10 iterations)
- Resistant aux attaques par force brute (GPU-resistant)

Les mots de passe ne sont JAMAIS stockes en clair dans la base de donnees.

Verification lors de la connexion (ligne 85) :
   const isPasswordValid = await bcrypt.compare(password, visiteur.password);

PRATIQUE 4 : IMPLEMENTER UN RATE LIMITING

Implementation : src/middlewares/Ratelimiter.ts

Configuration (lignes 3-11) :
   export const apiLimiter = rateLimit({
     windowMs: 1 * 60 * 1000,  // 1 minute
     max: 10,                   // 10 requetes maximum
     message: {
       error: "Trop de requetes. Reessayez dans 1 minute."
     },
     standardHeaders: true,
     legacyHeaders: false,
   });

Application (src/server.ts ligne 68) :
   this.app.use('/api', apiLimiter);

Cette limitation protege contre :
- Les attaques par force brute (essais de mots de passe)
- Les attaques DDoS (deni de service)
- Le scraping abusif de l'API
- La surcharge du serveur

PRATIQUE 5 : CONFIGURER CORS DE MANIERE RESTRICTIVE

Implementation : src/server.ts (lignes 54-59)
   this.app.use(cors({
     origin: process.env.NODE_ENV === 'production'
       ? process.env.ALLOWED_ORIGINS?.split(',')
       : '*',
     credentials: true
   }));

En developpement : origine '*' (tous les domaines)
En production : uniquement les domaines listes dans ALLOWED_ORIGINS

Cela empeche des sites malveillants de faire des requetes vers notre API
depuis le navigateur des utilisateurs.

PRATIQUE 6 : NE PAS EXPOSER DE DONNEES SENSIBLES

Implementation : src/services/Visiteur.ts

Exclusion systematique du mot de passe dans les reponses :

- Apres creation de compte (lignes 60-61) :
  const visiteurSansPassword = await VisiteurModel.findById(visiteur._id).select('-password');

- Apres connexion (ligne 96) :
  const visiteurSansPassword = await VisiteurModel.findById(visiteur._id).select('-password');

- Dans getAllVisiteurs (ligne 114) :
  .select('nom prenom email portefeuille')

- Dans getVisiteurById (ligne 128) :
  .select('nom prenom email portefeuille')

Le hash du mot de passe n'est JAMAIS renvoye au client.

PRATIQUE 7 : UTILISER DES VARIABLES D'ENVIRONNEMENT

Implementation : Fichier .env a la racine

Variables sensibles stockees dans .env :
- DB_USERNAME
- DB_PASSWORD
- DB_NAME
- JWT_SECRET
- PORT
- NODE_ENV
- ALLOWED_ORIGINS

Chargement (src/server.ts ligne 23) :

PRATIQUE 8 : ENCODER LES CARACTERES SPECIAUX DANS LES URLS

Implementation : src/config/database.ts (ligne 53)
   const encodedPassword = encodeURIComponent(dbPassword);

Si le mot de passe de la base contient des caracteres speciaux (@, #, /, etc.),
ils doivent etre encodes pour ne pas casser l'URI de connexion MongoDB.

PRATIQUE 9 : GERER LES ERREURS SANS EXPOSER DE DETAILS SENSIBLES

Implementation : Dans tous les controleurs

Exemple (src/controllers/Visiteur.ts lignes 38-43) :
   catch (error: any) {
     res.status(400).json({
       success: false,
       message: error.message || 'Erreur lors de la creation'
     });
   }

On renvoie uniquement un message generique au client, pas la stack trace
complete ni les details de l'erreur interne qui pourraient aider un attaquant.

Les erreurs detaillees sont loggees cote serveur (console.error) mais jamais
exposees au client.

PRATIQUE 10 : UTILISER UNE AUTHENTIFICATION STATELESS (JWT)

Implementation : src/middlewares/auth.ts et src/services/Visiteur.ts

Le systeme JWT est stateless : pas de session stockee cote serveur.
Avantages pour la securite :

- Pas de stockage de sessions en memoire (moins de risques de vol)
- Tokens signes cryptographiquement (impossible a falsifier)
- Expiration automatique (1 heure)
- Verification de l'algorithme pour eviter les attaques "none algorithm"

6.2 - Bonnes pratiques de securite a mettre en oeuvre

Voici les bonnes pratiques recommandees par ExpressJS qui ne sont PAS encore
implementees dans notre projet, avec des explications sur comment les realiser.

PRATIQUE A IMPLEMENTER 1 : UTILISER HTTPS EN PRODUCTION

Actuellement : Le serveur ecoute en HTTP (pas de certificat SSL/TLS).

Risque : Les donnees (dont les tokens JWT et mots de passe) sont transmises
en clair sur le reseau. Un attaquant en position de man-in-the-middle peut
intercepter les communications.

Solution :

A. Obtenir un certificat SSL/TLS :
   - Let's Encrypt (gratuit, automatique)
   - Certificat paye aupres d'une autorite de certification
   - Certificat auto-signe pour le developpement uniquement

B. Configurer Express pour utiliser HTTPS :

   Dans server.ts :
   import https from 'https';
   import fs from 'fs';

   const options = {
     key: fs.readFileSync('path/to/private-key.pem'),
     cert: fs.readFileSync('path/to/certificate.pem')
   };

   https.createServer(options, this.app).listen(this.port);

C. Forcer HTTPS avec Helmet :
   this.app.use(helmet.hsts({
     maxAge: 31536000,
     includeSubDomains: true,
     preload: true
   }));

D. Rediriger HTTP vers HTTPS :
   this.app.use((req, res, next) => {
     if (req.protocol === 'http' && process.env.NODE_ENV === 'production') {
       return res.redirect(301, `https://${req.headers.host}${req.url}`);
     }
     next();
   });

PRATIQUE A IMPLEMENTER 2 : METTRE EN PLACE UN SYSTEME DE LOGGING DE SECURITE

Actuellement : Quelques console.log() mais pas de systeme de logging structure.

Risque : Impossible de detecter des tentatives d'intrusion, d'analyser les
incidents de securite, ou de respecter les obligations de traçabilite.

Solution : Utiliser une bibliotheque de logging comme Winston ou Pino.

Installation :
   npm install winston

Configuration (creer src/utils/logger.ts) :

   import winston from 'winston';

   export const logger = winston.createLogger({
     level: 'info',
     format: winston.format.combine(
       winston.format.timestamp(),
       winston.format.json()
     ),
     transports: [
       new winston.transports.File({ filename: 'logs/error.log', level: 'error' }),
       new winston.transports.File({ filename: 'logs/security.log', level: 'warn' }),
       new winston.transports.File({ filename: 'logs/combined.log' })
     ]
   });

   if (process.env.NODE_ENV !== 'production') {
     logger.add(new winston.transports.Console({
       format: winston.format.simple()
     }));
   }

Evenements a logger :

- Tentatives de connexion echouees (trop de tentatives = brute force)
- Acces refuses (tokens invalides, headers manquants)
- Erreurs d'authentification (visiteur inexistant, mauvais mot de passe)
- Operations sensibles (creation/suppression de comptes, modifications importantes)
- Erreurs serveur 500

Exemple dans auth.ts :
   catch (error) {
     logger.warn('Tentative d\'acces non autorisee', {
       ip: req.ip,
       url: req.url,
       method: req.method,
       error: error.message
     });
     res.status(401).json({ error: 'Unauthorized request' });
   }

PRATIQUE A IMPLEMENTER 3 : IMPLEMENTER UNE BLACKLIST DE TOKENS JWT

Actuellement : Un token reste valide jusqu'a son expiration (1h), meme si
l'utilisateur se deconnecte ou si le compte est compromis.

Risque : Impossible de revoquer un token avant son expiration naturelle.

Solution : Maintenir une blacklist des tokens revoques.

Implementation avec Redis (cache rapide) :

A. Installation :
   npm install redis ioredis
   npm install --save-dev @types/ioredis

B. Configuration Redis (creer src/config/redis.ts) :
   import Redis from 'ioredis';

   export const redisClient = new Redis({
     host: process.env.REDIS_HOST || 'localhost',
     port: parseInt(process.env.REDIS_PORT || '6379'),
     password: process.env.REDIS_PASSWORD
   });

C. Methode de deconnexion (ajouter dans Visiteur.ts service) :
   public async seDeconnecter(token: string): Promise<void> {
     const decoded = jwt.decode(token) as any;
     const expirationTime = decoded.exp - Math.floor(Date.now() / 1000);

     await redisClient.setex(
       `blacklist:${token}`,
       expirationTime,
       'revoked'
     );
   }

D. Verification dans le middleware auth.ts :
   // Apres jwt.verify()
   const isBlacklisted = await redisClient.get(`blacklist:${token}`);
   if (isBlacklisted) {
     throw new Error('Token has been revoked');
   }

E. Route de deconnexion (ajouter dans Visiteur.ts routes) :
   router.post('/deconnexion', authMiddleware, controller.seDeconnecter);

PRATIQUE A IMPLEMENTER 4 : VALIDER LE TYPE DE CONTENU DES REQUETES

Actuellement : Aucune verification du Content-Type des requetes.

Risque : Un attaquant pourrait envoyer du contenu inattendu (XML, multipart)
qui pourrait etre mal interprete ou exploiter des vulnerabilites.

Solution :

Dans server.ts, apres express.json() :

   // Middleware de validation du Content-Type
   this.app.use((req, res, next) => {
     if (req.method === 'POST' || req.method === 'PUT' || req.method === 'PATCH') {
       const contentType = req.headers['content-type'];

       if (!contentType || !contentType.includes('application/json')) {
         return res.status(415).json({
           error: 'Content-Type doit etre application/json'
         });
       }
     }
     next();
   });

PRATIQUE A IMPLEMENTER 5 : IMPLEMENTER UNE POLITIQUE DE MOT DE PASSE FORTE

Actuellement : Validation basique (8 caracteres, majuscule, minuscule, chiffre).

Risque : Mots de passe faibles vulnerables aux dictionnaires et patterns courants.

Solution : Utiliser la bibliotheque zxcvbn pour evaluer la force reelle.

Installation :
   npm install zxcvbn
   npm install --save-dev @types/zxcvbn

Dans validation.ts :
   import zxcvbn from 'zxcvbn';

   body('password')
     .custom((value) => {
       const result = zxcvbn(value);
       if (result.score < 3) {
         throw new Error(`Mot de passe trop faible. ${result.feedback.warning}`);
       }
       return true;
     })

Autres ameliorations :
- Verifier contre une liste de mots de passe compromis (Have I Been Pwned API)
- Empecher la reutilisation des 5 derniers mots de passe
- Forcer un changement de mot de passe tous les 90 jours

PRATIQUE A IMPLEMENTER 6 : LIMITER LA TAILLE DES REQUETES

Actuellement : Pas de limite explicite sur la taille du body.

Risque : Un attaquant peut envoyer des payloads enormes pour saturer la
memoire du serveur (attaque par epuisement des ressources).

Solution :

Dans server.ts :
   this.app.use(express.json({ limit: '10kb' }));
   this.app.use(express.urlencoded({ extended: true, limit: '10kb' }));

10 Ko est suffisant pour toutes nos requetes normales. Tout ce qui depasse
sera rejete avec une erreur 413 (Payload Too Large).

PRATIQUE A IMPLEMENTER 7 : IMPLEMENTER L'AUTHENTIFICATION A DEUX FACTEURS (2FA)

Actuellement : Authentification simple (email + mot de passe uniquement).

Risque : Si un mot de passe est compromis, le compte est entierement vulnerable.

Solution : Ajouter un deuxieme facteur (TOTP - Time-based One-Time Password).

Installation :
   npm install speakeasy qrcode
   npm install --save-dev @types/speakeasy @types/qrcode

Etapes :

A. Ajouter des champs au modele Visiteur :
   twoFactorSecret: { type: String, required: false },
   twoFactorEnabled: { type: Boolean, default: false }

B. Route pour activer 2FA (generer le QR code) :
   router.post('/2fa/setup', authMiddleware, controller.setup2FA);

   Controleur :
   const secret = speakeasy.generateSecret({ name: 'GSB API' });
   await visiteurService.update(req.auth.visiteurId, {
     twoFactorSecret: secret.base32
   });
   const qrCodeUrl = await qrcode.toDataURL(secret.otpauth_url);
   res.json({ qrCode: qrCodeUrl });

C. Modifier la connexion pour demander le code TOTP :
   body('totpCode').optional().isLength({ min: 6, max: 6 })

   Dans seConnecter() :
   if (visiteur.twoFactorEnabled) {
     const isValid = speakeasy.totp.verify({
       secret: visiteur.twoFactorSecret,
       encoding: 'base32',
       token: totpCode
     });
     if (!isValid) {
       throw new Error('Code 2FA invalide');
     }
   }

     userAgent: { type: String, required: true },
     timestamp: { type: Date, default: Date.now },
     details: { type: Schema.Types.Mixed, required: false }
   });

Middleware d'audit (src/middlewares/audit.ts) :
   export const auditMiddleware = (action: string) => {
     return async (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
       const originalSend = res.send;

       res.send = function(data) {
         if (res.statusCode < 400) {
           AuditLogModel.create({
             userId: req.auth?.visiteurId,
             action,
             resource: req.path,
             resourceId: req.params.id,
             ipAddress: req.ip,
             userAgent: req.get('user-agent'),
             details: { method: req.method, body: req.body }
           });
         }
         return originalSend.call(this, data);
       };

       next();
     };
   };

Application :
   router.delete('/:id', authMiddleware, auditMiddleware('DELETE_VISITEUR'), controller.delete);

PRATIQUE A IMPLEMENTER 10 : SCANNER LES DEPENDANCES POUR LES VULNERABILITES

Actuellement : Pas de verification automatique des dependances.

Risque : Utiliser des versions de bibliotheques avec des vulnerabilites connues.

Solution :

A. Utiliser npm audit :
   npm audit
   npm audit fix

B. Installer et configurer Snyk :
   npm install -g snyk
   snyk test
   snyk monitor

   Dans .github/workflows/security.yml :
   - name: Run security audit
     run: |
       npm audit --audit-level=moderate
       npm run test

D. Mettre a jour regulierement :
   npm outdated
   npm update

   Creer .github/dependabot.yml :
   version: 2
   updates:
     - package-ecosystem: "npm"
       directory: "/"
       schedule:
         interval: "weekly"
